# hf_ally changelog (development history, newest first is NOT guaranteed; see git tags)

* **v0.16.2 (callback-local battle views):** collect both ally panels' render-body and existing HUD-marker identities in one pass per table, memoize guarded owner reads only during discovery, and index duplicate membership without changing native marker order, layers or scale. Sprite-layer enumeration no longer allocates a vector per sprite. Interceptor target selection streams the native active-body array instead of allocating an all-body snapshot on every hunt; search frequency, native active predicates and target priority/tie order are unchanged. Precombat cleanup is a screen-exit transition with incomplete-scan retries, not two full GUI walks on every armed combat tick. Precombat lifetime/layout checks share one complete GUI scan per tick, and fixed-name comparisons no longer allocate strings for unrelated GUI elements. Debug probes validate creature-list pages once per callback, retain roster membership checks before reading cached objects, and still count weapons every tick. Aircraft census/watch/loadout-verification diagnostics now require `logging.debug_log`; gameplay tracking and event logs remain. Disabled snapshots no longer allocate reason strings, and the watchdog builds heartbeats only when due. No new config keys, dependencies, or persistent native-pointer caches. Existing panel/aircraft notes checked against live Ghidra; validation details in `docs/ally-performance.md`. Game not run; in-game verification pending.

* **v0.16.1 (retire `enemy_all_at_once`):** remove the key and its 30 s timer patch. The setting only skipped the stock initial reinforcement wait; it did not change the enemy list, active group size or later wave timing, so it was not worth a config switch. `enemy_group_size` remains the control for enemies active at once, and the stock 30 s refill delay now always applies. An old `enemy_all_at_once` key is ignored. The preset drops the key. Also remove four unused constants/helpers and fix the `on_click_pre` function-pointer cast warning; no behaviour change. Cross-build only; in-game verification pending.

* **v0.16.0 (retire `auto_retreat`):** `auto_retreat` was only an enable/disable wrapper around `flagship_leaves`; when false, the mod left the stock game to promote an ally and the retreat point stayed consumed. Retire it: `flagship_leaves` always applies. `"handover"` (default) promotes an ally and restores the retreat point; `"retreat"` extracts the squad and ends the battle as a retreat. An invalid `flagship_leaves` now logs a warning and falls back to `"handover"` instead of silently acting as `"retreat"`. An old `auto_retreat` key is ignored. No other config changes. Cross-build only; in-game verification pending.

* **v0.15.0 (public release: config cleanup, localized radio lines, honor sharing):** first public pack since v0.14.22. `ally.json` is grouped and carries no retired keys: `enabled` is the only master switch; `spawn_ally`, `ally_toggle`, `ally_reticles`, `max_enemy_ships`, `plane_bombers`, `marker_seam`, `marker_delay_ms` and the retired logging keys are ignored. `ally_reticle_scale` controls both visibility and size; `ally_honor_share` (new, default `0.5`) gives every deployed ally 50% of the player's earned battle honor/XP. Ally radio lines follow the game language: Russian from `Media/Snd/RADIO`, English from `Media/Snd/RADIO_ENG`; a live language switch applies to the next line. Custom voice paths and custom audio are future work. Validated in game on 2026-11-07 (config cleanup, language switch, honor sharing); release pack v0.15.0.

* **v0.14.27 (ally honor sharing):** new `ally_honor_share` (default `0.5`): every deployed ally earns a share of the player's in-battle honor. The player keeps the full award; each ally gets `share ×` the player's award as it is earned. `0` disables sharing, `1` gives allies the full award; values outside 0..=1 are clamped and non-finite values use 0.5. The battle honor field (`Creature+0x1a24`) is the same one the stock battle manager fills and `SCR_COMBAT_ReturnToMap` converts to `m_xp`, so allies keep the share after the fight and it counts toward their stars/promotions. Only allies deployed in the battle share; late joiners earn from then on, and a ship that leaves stops earning. The new hook is installed only when the effective share is above 0 and is byte-checked against the 1.163 award site. The battle-end `ALLY SUMMARY` line prints the player's earned honor and the total shared with allies. No other config changes. In-game validation passed (2026-11-07).

* **v0.14.26 (language-aware ally radio lines):** `ally_sounds` now plays the line in the game's current language. The mod reads `coreLanguage` (1 = Russian, 2 = English) when a line starts and appends `_eng` in English, exactly like the stock radio's `String_AppendEngSuffix` (0x1401b20f0): plain `sound.res` names resolve to `Media/Snd/RADIO` and `_eng` names to `Media/Snd/RADIO_ENG`. A language change in the options applies to the next line without a restart. Every line the mod plays has an English variant. The pre-combat `button_01` click is a UI sound and is not localized. No configuration changes. In-game validation passed (2026-11-07).

* **v0.14.25 (retire `ally_reticles`):** the boolean is gone; `ally_reticle_scale` now controls both the size and visibility of the ally target boxes. `0` disables them, a positive finite value sets the size relative to the native 62 x 62 frame, and negative or non-finite values fall back to `0.8` with a warning. An old `ally_reticles: false` is ignored; set `ally_reticle_scale: 0` instead. The player's own box is unchanged, and the debug overlay still installs when the scale is 0. In-game validation passed (2026-11-07).

* **v0.14.24 (retire `spawn_ally` and `ally_toggle`):** `enabled` is now the only master switch. When it is true, the wingman deploys and the pre-combat UI is always installed; `false` installs no gameplay hooks (the crash reporter still loads). The old keys are ignored: `spawn_ally: false` no longer suppresses allies and `ally_toggle: false` no longer hides the ALLY/plane-loadout buttons or the `PLAYER` label. Use the per-ship ALLY toggle on the pre-combat card to skip the wingman, or `enabled: false` to turn off the whole mod. This removes the separate "other features without allies" mode, because the mod is an ally mod first. In-game validation passed (2026-11-07).

* **v0.14.23 (pre-combat click debounce):** the ALLY toggles and carrier plane-loadout buttons now debounce per button at 120 ms instead of sharing one 350 ms window. The game can deliver one physical click twice (press and release), but the old window also swallowed deliberate clicks on any of these buttons within 350 ms, including a different button. No configuration changes. In-game validation passed (2026-11-07); first included in the public v0.15.0 pack.

* **v0.14.22 (retire `max_enemy_ships`):** remove the key and its patch. The old one-byte patch at `0x1402caaa0` was inside `SCR_BOMBERS`, the strategic bomber scene setup, not `SCR_COMBAT`; normal tactical combat fills its enemy list through `Precombat_SplitFleetIntoReserveLists` with no total cap. The setting therefore did nothing in normal battles, where vanilla uses every ship in the engagement. `enemy_group_size` is the real control for enemies active at once: `Battle_DeployFromReserve` uses it for the initial group and for refills after the 30 s timer. Rename the wave module from `max_enemy` to `enemy_waves` and document the correct semantics. In-game validation passed (2026-11-07).

* **v0.14.10 (ally panel marker layers):** v0.14.9 called `Body::UpdateHudMarkers` `0x14002d7b0(ally, 1)` and logged "produced 0 part markers" in a real battle: the function returns before doing anything unless the node state (`+0x48`) is at least 2 and the body opacity (`+0x8f8`) is positive, and it only walks children that pass the same gates, so a deployed ally still never entered the table. The panel no longer relies on that call. It writes the type-2 records itself, for one call only, reproducing the native layer and scale rules: layer = sprite stage `+0x114` + 4 * part floor `+0x9b8` + inherited stage (`Body_GetInheritedStage` `0x140033b00`), a four-layer depth range for sprites whose `+0x50` bit 0 is set, and scale `1 - 0.05 * (top - layer)`. Records already present in layers 1..39 are skipped, so a ship that *was* registered natively (the previous player ship after a control handoff) is not drawn twice. This also fixes the appearance of the previous fallback, which put every record in layer 1: the panel lifts brightness by `layer / 40` and draws layers in order, so one low layer left the hull near-black and let modules paint over it ("only parts are visible"). `Hud_DrawChildMarker` `0x1402e08b0` draws type 2 only. Log line: `ALLY panel c=...: N parts -> M part markers in layers a..b (...)`.

* **v0.14.9 (ally panel native marker initialisation):** the missing piece was `Body::UpdateHudMarkers` (`0x14002d7b0`) with `initialise = 1`. The stock spawn path makes that one call, which sets the body's HUD-initialised byte (`+0x910`) and registers type-2 part markers for the whole child subtree. The per-frame pass then keeps them current for every body that has the byte set. Because the mod's temporary ally deploy skipped the call, the per-frame pass left every ally part alone, which is why the panel showed text (and, after the v0.14.6-8 workarounds, synthetic geometry) instead of the stock schematic. The panel now performs that native initialisation before rendering an ally that has no markers, so the ally is drawn by the same path, palette, layer and scale as an enemy panel. The synthetic-marker fallback remains only for the case where native initialisation still yields nothing.

* **v0.14.8 (ally panel hull markers):** the v0.14.7 native registration did not populate markers for the temporary ally, so the fallback still drew only mounted modules. The part source now merges the **main battle render body grid** (`DAT_146449688`, the same grid the enemy target/module view uses) with the creature's mounted-part vector. Hull bodies present only in the render grid are included, deduplicated against existing visible markers, and added to layer 1 with the normal palette/brightness. The log reports the merged part count and built/existing/inactive markers.

* **v0.14.7 (ally panel native marker registration):** the v0.14.6 attempt still left the ally schematic incomplete because the temporary ally deploy path skipped `Hud_RegisterMarkerForBody` (`0x14011c760`), the registration the stock enemy/player spawn path runs. The panel now calls that native function once per ally per battle when no visible child markers exist, using the same complete part/sprite marker table as enemy panels. If native registration still leaves gaps, the bounded fallback builds only the missing markers, skips markers already visible in layers 1..39, and appends them to layer 1 so the panel's normal palette and brightness lift are preserved. Details: `hf_notes/docs/rendering/battle-ship-panels.md`.

* **v0.14.6 (ally panel rendering and despawn):** the extra ally panels now use the native `SetLink` for the temporary target instead of writing `player+0xb00` directly, matching the stock target panel's link state. The temporary ally deploy path does not reliably leave type-2 part markers in the native HUD marker table, so the panel drew its text but no ship. The mod now builds child markers from the ally's real part/sprite lists for the call, skipping any part marker already visible in layers 1..39 and placing only the missing ones in layer 1, then removes them immediately. Layer 1 preserves the panel's normal palette; the first attempt used layer 39, whose `layer / 40` brightness lift made the ship milky white. Panels are hidden on the same message/end-screen gate as the stock target panel, retreating/leaving allies (`+0xbdc` 2) are excluded, and a frame with no rendered ally clears the cached panel content so last-frame textures cannot survive a battle. * **v0.14.5 (combat ship switching):** new `ship_switching` option (default **true**). **1** takes the ally shown in the top ship panel, **2** the bottom panel, and **TAB** cycles deployed friendly ships in roster order (the original player ship is included; reserve ships are not). The selected ship becomes player-controlled at the next battle-manager tick, keeps its panels/tracking slot and its former player ship becomes an ordinary AI ally, so F8/fuel retreat and `hf_ai` treat it as one. Held gun/flare/boost input moves to the new ship; a pending bomb command does not. The player ship is not in the native AI vector at spawn, so the swap appends it there with the game's own Link helpers and removes the newly flown ship from that vector, preventing the AI task from fighting player input. All helpers are byte-checked before the battle hook is installed. Keys act once per press and are ignored in pre-combat, paused time, dialogs and when another window has focus. First build refused every swap because the AI-list check was wrong; fixed and confirmed in game. Details, native evidence and test checklist: `docs/ship-switching.md`.

* **v0.14.3 (ally ship bombers):** new `ally_bombers` option (default **false**) gives bomb-carrying wingmen a player-like bombing run. Dive and aim use the same world direction for the swivel (0x64/0x65) and thrust (0x66/0x67) commands every tick, as the player's controls do. Descent is governed so the ship can still pull out (up to 220 u/s, 85% of the achievable descent, 80% of available lift, 80-unit hull margin). Aiming follows the native ballistic prediction at 10 Hz with proportional plus damping correction. The whole payload is released on one landed, non-prize target at 0.05 s intervals once the shot is inside the target's bounding radius, at most 1000 units above it and with real downward speed; a run that starts below that ceiling qualifies immediately. A usable shot is accepted either from the native hit flag or from the predicted miss, and for 0.5 s after the pull-out starts so the steering guard cannot steal it. While bombs remain the ship fires flares every 0.5 s and ship-missile launches are blocked. After the salvo it continues horizontally while pulling up for at least 1.5 s. Boost is suppressed at 350 native engine temperature. Airborne and prize/trader targets are never attacked, regardless of `spare_prizes`. Validated in game by the maintainer; heat behaviour and edge cases still need broader testing.

## Side patch: `intercept_ignore_oids` (branch `side/ignore-intercept-oids`, never merged to master)

For modders who made an anti-air missile (a Sprint) strategic-launchable by giving it the category bit `0x8000000` in `OL.seria`. In the missile-vs-ship arcade scene the AI of **both** sides then counts that missile as a strategic launch to intercept, even when its own side launched it: the CIWS and the anti-air launchers fire at it and it takes priority over the real incoming missile.

Config (`Modloader/config/ally.json`), empty by default (= vanilla):

"intercept_ignore_oids": ["MDL_MISSILE_03"]

`MDL_MISSILE_03` is the stock R-9 Sprint; use the exact `m_oid=` names from `OL.seria` (case-sensitive, one entry per part; a clone with its own oid needs its own entry). The log line `INTERCEPT candidate: strategic-launch body oid=...` lists the first 12 distinct oids the AI saw as strategic launches, so a wrong name shows up after one battle. A listed part is never put on any AI ship's interception list; the AI picks the next real threat. It works without `spawn_ally`. Log lines: `hf_ally: AI ignores these parts...` at start and `INTERCEPT ignore: body=... oid=...` the first time each missile is skipped. Untested in play as of v0.12.11-ignoreoid.1. Site: `0x140062812` (`docs/findings/ai/ai-intercept-targets.md` in hf_notes).
